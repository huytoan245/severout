# Family Location 2.3.2 / code36: permanent first install and same-device rebind

Review boundary: no production mutation, pepper deployment, release signing or phone installation is authorized by this candidate. Historical v231 commit `530f27a4c82ed14831eb7d7597aa5dc5f679c5dd`, its private capabilities, APKs and production evidence remain available unchanged. PR27 stays Draft and unmerged.

The v231 design tied first claim to a seven-day capability and rejected a different UID/key after uninstall. It had no stable binding to authorize a new installation. V232 separates permanent one-time initial claim, ordinary runtime proof, same-device rebind, and offline operator recovery.

## Client and server contract

`DeviceRecoveryBindingProvider` reads ANDROID_ID locally and the actual APK signer certificate. Release builds require the existing pinned certificate `62b909ff3c5e6b56565cfe2814913778acdf694f32a042f12bc05c35404ed63f`. It hashes newline-separated `FamilyLocation-v232`, `family-01`, role, package (`com.family.parent`/`com.family.child`), lowercase signer hex, lowercase ANDROID_ID. UID, installation key and app version are excluded. Neither raw ID nor the resulting recovery credential enters logs, UI or server storage. Parent and Child materials differ.

The server stores HMAC-SHA256 using a canonical base64url 32-byte `DEVICE_BINDING_PEPPER` over newline-separated `FL232-BIND`, `family-01`, role, recovery material. This additional server domain separation prevents cross-role equality even for a malicious equal input. The pepper is independent of bootstrap capabilities and the APK release signer. Generate it once, protect an offline operator backup, stage only as a Cloudflare secret after review, and preserve it indefinitely. Missing/changed pepper rejects recovery; loss requires explicit operator recovery. This candidate does not create or stage a production pepper.

Fresh Parent/Child capabilities are independent CSPRNG 256-bit values. The public manifest contains only hashes and fixed scopes, `bootstrapMode=UNTIL_CONSUMED_OR_REVOKED`, and no `expiresAt`. This implements VALID_UNTIL_CONSUMED_OR_REVOKED semantics. Initial capability stays valid for months until consumed/revoked. Server stores no capability plaintext. Initial UID/key, binding hash, consumption and generation are one conditional family commit. Failed commits expose none of these fields partially. Runtime proofs omit the consumed capability.

EnrollmentManager uses anonymous Firebase Auth, the retained installation key for APK updates, and a durable proof journal. An occupied slot triggers RebindManager automatically. A new installation creates a new nonexportable P-256 Android Keystore key. A retained retired anonymous UID is replaced once automatically, still requiring the binding match. Rebind always requires a fresh anonymous UID; an existing UID with a replacement key receives fresh_identity_required and Android automatically renews anonymous Auth once. This revokes the old UID Firestore JWT, which Rules cannot bind to a P-256 key. SDK backup is disabled for both apps. Only Registered/Rebound/Recovery required membership states are shown in Parent Health; Child UI is unchanged.

Worker routes: `/health`, `/v1/challenge`, `/v1/register/parent`, `/v1/register/child`, `/v1/rebind/parent`, `/v1/rebind/child`, `/v1/family`, `/v1/token`, `/v1/wake`, `/v1/diagnostics`. Fixed family-01/child-01, bounded bodies, JWT verification, P-256 proof, per-UID/global rate limits and durable nonce replay protection remain. Nonces bind UID, role, purpose, epoch and generation and expire after two minutes; this short proof validity does not expire initial bootstrap.

Rebind verifies fresh JWT, new-key proof and constant-time binding hash match. A Firestore documents:commit atomically replaces UID/key, increments epoch and role generation, retains the binding, appends a hash-only audit, and for Child clears FCM token/owner and advances token generation using Child updateTime CAS. No coordinate, event or journey write is included. Token sync rebases and confirms the fresh token against the new mapping. Previous UID is retired by hash; the old public key is recorded as a hash in the audit and permanently added to retiredKeyHashes. Rebind cannot reuse the current key or a retired key. If installation data/Auth was cleared but Android retained a key, fresh_key_required makes the client renew only its installation P-256 key once; ordinary APK update never rotates that key. A same-UID key replacement cannot rebind until Android obtains a fresh UID; every authoritative rebind retires the previous UID.

An exact committed proof retry within its nonce deadline receives its committed result without another epoch increment, including server restart or loss of the first HTTP response. A modified or cross-purpose proof is rejected. After nonce expiry, the same authoritative UID/key may resume registration without bootstrap. Only one conflicting CAS can become authoritative. There is no takeover fallback to model, name, IP, package, signer, FCM token or timestamps.

Mutating Worker operations check the current UID/key and nonce epoch. Firestore SDK/REST authorization uses the current server-managed UID mapping; Firestore Rules cannot verify an Android P-256 proof. Client family mapping and server fields are immutable. Parent commands and reminder requests carry family epoch, including HTTPS fallback. Child command stage/ACK writes require the active epoch; old pending wake jobs also fail the server epoch guard. Ordinary GPS/event writes remain authorized for the current Child. History remains under logical child-01. Commands from a previous epoch can require a fresh Parent request; they are never silently rebound.

## Offline migration and recovery

`migration-plan-v232.mjs` has no apply/deploy/credential option. It requires a fresh protected admin snapshot, unclaimed Parent/Child UID/key, both consumed flags explicitly false, no claim/binding evidence, original family updateTime and a new hash-only manifest. Initial provisioning is create-only if absent; an existing unclaimed v231 family uses CAS. It rejects claimed/ambiguous/missing-revision state or old-hash reuse. The proposal retires both v231 hashes, removes both initial expiry fields, sets schema232/permanent mode and increments epoch. Only the family document is written; devices/events/location/history are preserved. The old v231 protocol and capabilities cannot claim after migration.

The exported offline `recoveryPlan` is separate from public HTTP. For one selected role it retires UID/key/binding hashes, increments epoch/generation, clears the slot, installs a fresh recovery hash with `RECOVERY_EXPIRING` and a maximum 24-hour expiry, and creates an audit. Child recovery also clears token authority in the same CAS commit. The other role and all history remain. The operator must securely deliver the short-lived capability in a separately reviewed private build; it is never an APK master secret. Recovery does not rotate the release signer.

Production migration after human review must:

1. Re-read active Worker, Rules and family/device revisions; back up document data and event inventory privately. Compare against the reviewed proposal. A changed revision or newly claimed slot means STOP and a new migration review.
2. Preserve the existing Google secret. Generate/back up a stable pepper on the operator host without displaying it, stage it in an undeployed coordinated code+secret version, and verify OAuth/Firestore/FCM authentication without real device delivery.
3. Enter a reviewed brief maintenance window. Deploy schema232 Worker with staged pepper, apply the reviewed family CAS, then publish compatible Rules. During the schema mismatch enrollment fails closed. These three services cannot share one distributed atomic commit; do not describe this as atomic cross-service deployment. If a phase fails, keep enrollment closed, inspect recorded state, and roll back only using matching backed-up code/rules/schema. Never reopen consumed hashes or overwrite a claimed mapping.
4. Verify version/configured, active code+secrets, family schema/hash-only state, no expiry, retired old hashes, role endpoints, Rules source and unauthorized reads, server auth, and exact preservation of all pre-existing documents/events. A health 200 alone is insufficient.
5. Only then authorize local SecureString signing with the unchanged JKS. Both package/version/code/certificate/apksigner/16KiB zipalign gates must pass before either Installable is published. Stop again before phone installation.

## Security and data limits

ANDROID_ID is a practical private-device recovery signal, not hardware attestation. Android 8+ scopes it to signing key, Android user and device ([Android reference](https://developer.android.com/reference/android/provider/Settings.Secure#ANDROID_ID)). Automatic recovery is intended for the same physical device, same user/profile and same release signing identity. Factory reset, new phone/profile, ID reset, signer change or the documented pre-Android-8 OTA uninstall exception requires operator recovery. Do not promise reinstall forever on every device.

A leaked private APK before its first claim can expose its permanent initial capability and permit a race. Keep private APKs private; initial no-expiry increases the duration of that risk. A rooted/compromised phone or stolen recovery material can defeat this practical signal. Fresh JWT and new-key possession do not establish physical hardware identity. HMAC protects stored binding and role scopes; it does not turn ANDROID_ID into hardware attestation. No proof/material/capability is logged.

Reinstall preserves cloud events/location/journey and the logical device. Android uninstall/clear-data removes local SQLite: unsynced local samples cannot be restored by this design. APK update retains the existing key, UID and SQLite journal. Tracking, Journey merge behavior (5000+ records), offline journal, FCM wake, network failover, Child UI, 220 tips, six-hour reminder eligibility and existing request TTLs remain. Physical tests are still required.

Verify new UID/key, same binding, epoch/generation increment, cleared old token authority, same child-01, all existing cloud history, resumed GPS and FCM. Repeat Parent reinstall and verify Child remains paired and refresh works. Test ordinary APK update without uninstall and confirm no rebind. Then test process death, reboot, Doze, network loss and Samsung 24–48h. Never log ANDROID_ID or recovery material in evidence.
