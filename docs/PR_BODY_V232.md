First installation previously depended on a seven-day capability, and an uninstall lost the UID/device key accepted by the backend. V232/code36 uses permanent one-time initial capabilities and a role-scoped HMAC device binding to authorize automatic same-phone reinstall with a fresh Firebase UID and P-256 installation key.

Rebind requires a fresh anonymous UID (automatically renewed when necessary) so the old Firestore JWT loses authority. Rebind uses fixed family/device scope, fresh JWT, epoch/generation-bound durable nonce and new-key proof. A Firestore CAS commit replaces the identity, retires the old UID/key, increments epoch/generation and atomically clears Child FCM ownership. Exact committed retry after response loss does not increment epoch twice. Old identities and stale commands fail closed. No location/event/journey writes occur in rebind or initial migration.

Validation: 85 Worker tests; real workerd/SQLite endpoint/restart/rebind checks with intercepted Google traffic; 75 real Firestore emulator assertions including actual REST rebind CAS and old/new UID authorization; 91 paired signing/recovery regressions using mock APK gates; v231/v232 bootstrap boundary regressions; Android core/scenario and enrollment/Child unit tests; both release builds and full release lint with zero errors. Physical two-phone reinstall, GPS/FCM, reboot, Doze, process death and Samsung endurance remain unverified.

Production was read only: both slots remain unclaimed and v231 capabilities unconsumed. A fresh v232 hash-only CAS proposal retires old hashes/removes initial expiry; it has not been applied. Pepper is not configured/deployed. Source and unsigned private build are review candidates; signing, production migration/deployment and phone installation stop for human review. Public CI APKs contain no production capabilities. Existing release signer and historical v231 artifacts are preserved. PR27 stays Draft and unmerged; master is unchanged.

ANDROID_ID binding is a practical device/user/signer signal, not hardware attestation. Leaked first-claim APK capability can race enrollment; compromised devices or stolen recovery material remain risks. Factory reset/new device/profile/signer/ID change or pepper loss requires separate offline operator recovery. Cloud history persists; unsynced local SQLite cannot survive uninstall.
