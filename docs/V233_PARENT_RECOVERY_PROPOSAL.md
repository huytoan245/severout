## Separate Parent Recovery APK

Build with `-PparentRecovery=true -PupdateInPlace=true`, no bootstrap, and the operator transport public key. It retains com.family.parent/version2.3.3/code37 and the existing release signer. It has a separate RecoveryActivity launcher, PARENT_RECOVERY artifact gate and signing script; it is not the ordinary UPDATE APK repurposed as a fresh installer. The UPDATE manifest safeguard stays true to keep generic clients fail-closed, including after completion. Child source/APK is not updated or installed by this procedure.

Opening the Recovery APK only waits for Auth, reads alias/key usability, signs/verifies a local nonce using an existing key if present, and computes the existing scoped device binding material. Generic enrollment/wake/rebind is blocked while inspection is active. No new UID/key and no enrollment requests occur at startup. Flags on screen distinguish Auth PRESENT/NOT_OBSERVED_AFTER_WAIT, key PRESENT/ABSENT and usable/unusable. No raw identifiers appear.

Export is explicit and encrypted using AES-256-GCM, with its random AES key wrapped using operator RSA-OAEP SHA256/MGF1-SHA256. The separate operator encryption/approval key is DPAPI-protected outside Git; it is not an APK release signer or device enrollment key. No private key/Google credential/pepper goes into the APK. The report is transferred locally as a file; do not paste it or its decrypted contents into chat.

## Additional backend guard — source prepared, NOT DEPLOYED

The currently deployed v2.3.2 server has atomic CAS against the family it reads at execution time, but cannot bind a request to the exact earlier operator-approved revision. To meet the requested stop-on-state-change guarantee, this change adds optional `X-Family-Recovery-Guard` on Parent rebind/challenge: approved revision/epoch/generation/operationId are validated, bound to the nonce, echoed by digest, checked again before CAS and included in the create-only audit. Existing normal/Child protocols remain compatible.

This guard requires separately approved Worker deployment and the PUBLIC `PARENT_RECOVERY_OPERATOR_PUBLIC_KEY` variable matching the local case APK; Rules need no change. With that authority configured, all Parent rebind challenges/POSTs require its signed consent (including legacy callers); normal Parent registration/wake and Child protocols stay unchanged. The server verifies scope/expiry, approved revision/epoch/generation/operationId, old Parent UID hash and material hash, and binds the exact approval to the nonce. No private operator key is deployed. The Recovery APK checks `/health` for configured=true, parentRecoveryGuard=1 and the matching public operator-key digest **before any new Auth UID/key creation**. Today's production lacks that capability and therefore fails closed with `backend_guard_required`. Do not deploy automatically or silently fall back to unguarded rebind.

Approval must explicitly cover (a) deployment of the reviewed optional Worker guard, with the reviewed public authority key, without Rules/data migration, and (b) Parent-only creation of one fresh Anonymous Auth UID/installation key plus `/v1/rebind/parent` at the reviewed revision/epoch/generation. The two scopes can be approved separately. A signed approval file is private and short-lived: transfer it locally, never paste it in chat or include it in the release ZIP. The release signer/JKS/alias stay unchanged. No Child UID/key/token change, bootstrap creation, history deletion, Auth-user deletion or master merge is authorized.

After signed approval import and a separate on-phone confirmation, the client persists intent before Auth/key creation. It signs out the old local session only at this approved stage; it does not delete the old server Auth user. Process death/timeout resumes the same UID/key; an unresolved Auth creation stops instead of minting another user. Exact proof is journaled before POST. The server verifies Firebase project/token, same-device HMAC, server-verified signed operator approval, fresh UID/key, signature, nonce, approved snapshot and CAS. It atomically retires old Parent hashes and creates one audit. An update mask sends only Parent/epoch/retirement fields; Child and unrelated family metadata are not sent in that write. Expected epoch3→4/generation0→1 applies only if a fresh read still confirms that snapshot.

Child mapping/key/token and events/journey/location are preserved. The global epoch change invalidates pending old-epoch commands. After success the same recovered UID/key is cached for UPDATE protocol232 and the Parent dashboard opens. Validate history read and a newly issued command with the new epoch; no Child rebind or APK update is needed by the protocol. Real-phone behavior remains unverified.

## Failure and reconciliation

- Missing/mismatched binding, changed revision/epoch/generation, guard not deployed, expired/invalid approval => STOP. No blind mapping overwrite or new bootstrap.
- A pre-commit failure leaves mapping unchanged. A prepared Auth user/key can remain if a later guard/network/CAS check fails; retain that same operation and do not auto-delete users or generate replacements.
- Lost response: replay the exact proof while valid. If nonce expired, the same new UID/key must prove current Parent membership; otherwise re-challenge only against the unchanged approved snapshot, never a new identity. One atomic audit and one epoch increment are required.
- After committed rebind, do not restore retired UID/key or decrement epoch. Stop commands, keep protected snapshots/audit and review a forward recovery under fresh CAS and separate approval.
